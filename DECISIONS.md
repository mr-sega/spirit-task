# Решения

## Приём событий и хранение

Контроллер только вызывает действие и возвращает 204. Подпись проверяет middleware,
структуру и даты — Form Request с отдельными наборами правил. Приём события,
применение снимка и восстановление истории разделены на небольшие классы.

HMAC считается по исходным байтам тела, сравнивается через `hash_equals`.
Допустимое отклонение времени доставки — 300 секунд в обе стороны; время самого
события может быть старым. `X-Webhook-Id` должен совпадать с JSON. Подписанные строки
не обрезаются глобальными middleware. Секрет берётся из конфигурации; пустой секрет
даёт 503. Неверная подпись/время — 401, структура — 422, конфликт ID — 409.

Событие, заказ, позиции и история записываются в одной транзакции, затем возвращается 204. Уникальный ID события защищает от повторов; существующий ID с другим содержимым
отклоняется. Уникальный ID заказа и блокировка строки сериализуют одновременные
первые и последующие доставки. При ошибке изменения откатываются, повтор безопасен.
При дедлоке транзакция повторяется до трёх раз. Письма в HTTP-запросе не отправляются.

Неизвестные типы сохраняются без применения к заказу и получают 204. Это не создаёт
бесполезных повторов при расширении протокола; после добавления поддержки понадобится
отдельный механизм повторной обработки. Снимок заказа — источник состояния: более
свежее ручное исправление может вернуть статус назад. Позиции заменяются полностью,
`null` очищает прежние значения. Деньги хранятся в DECIMAL, без арифметики float.
Сумма маркетплейса сохраняется как есть; проверку расхождения расчёта следует согласовать
отдельно. Техническое время получения хранится у события, даты заказа — из маркетплейса
и нормализованы в UTC.

## Неоднозначности и принятые допущения

**Как определить порядок изменений одной секунды?** Нужен монотонный номер версии.
Пока сравниваем `(order.updated_at, event.created_at, event.id)`. ID сравниваем
лексикографически только для стабильного разрешения полной ничьей, не предполагая,
что ID содержит время. Это воспроизводимая политика, а не гарантия реального порядка.

**Как восстановить историю при пропущенных и запоздавших событиях?** Перестраиваем её
из сохранённых снимков конкретного заказа в том же порядке версий. Начало берём из
`order.created_at`, отсутствующую оплату — из `paid_at`, отмену — из `cancelled_at`.
Для доставки, получения и ручных исправлений используем `order.updated_at`.
Последовательные одинаковые статусы объединяются: обычный `order.updated` не создаёт
переход. Возврат к прежнему статусу сохраняется отдельным переходом. История отражает
известные снимки; неизвестные переходы и точное время статуса первого `order.updated`
невозможно восстановить без журнала маркетплейса. При исправлении уже известного
статуса старое `paid_at` не перемещает новый переход назад во времени.

**Какие ограничения считать допустимыми?** Суммы неотрицательные, до 12 целых цифр
и ровно двух дробных; количество — целое от 1 до 1 000 000, до 1000 позиций.
Поддерживаются даты с секундами и явной зоной, включая Z. Метки оплаты/отмены должны
попадать между созданием и изменением заказа. Тип события не задаёт жёсткий граф
переходов: актуальным считаем статус снимка, в том числе после ручной коррекции.
Лимиты и формат дробных секунд нужно подтвердить у маркетплейса.

## Следующие этапы и ограничения

В этом PR реализованы вебхуки и хранение. API заказов и письма — следующие PR.
Для писем нужен транзакционный outbox, отдельный ключ дедупликации уведомления и
проверка актуальности перед отправкой. Необходимо согласовать допустимые письма при
ручных исправлениях. SMTP не гарантирует exactly-once при падении между приёмом письма
и записью результата в БД; потребуется идемпотентный почтовый провайдер либо явная
политика спорных отправок.

Для небольшого тестового сервиса транзакция выполняется синхронно. При росте нагрузки
нужны durable inbox с быстрым подтверждением, фоновая обработка, метрики времени ответа
(лимит маркетплейса — 5 секунд), политика хранения персональных данных и мониторинг
повторов/ошибок. Перестроение всей истории удобно для корректности, но требует
оптимизации для заказов с большим числом событий.

Docker использует PostgreSQL, PHP 8.4, Node 24, очередь в БД и Mailpit. Vue/Inertia
выбран для будущей необязательной админки, чтобы сохранить один Laravel-проект.
Исходные материалы `task/` восстановлены после форматирования starter kit и исключены
из форматтеров: эталон подписи зависит от точных байтов JSON.

ИИ использован для подготовки кода, документации и тестов, проверки пограничных
сценариев и диагностики окружения. Решения и ограничения описаны здесь явно;
автоматические проверки не заменяют ревью.
