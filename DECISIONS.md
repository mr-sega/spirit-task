# Решения

## Структура и окружение

Контроллеры только вызывают действия и возвращают ответ. Валидация находится в Form
Requests и отдельных правилах, подпись — в middleware, JSON — в Resources. Логика
разделена на небольшие классы с ранними возвратами. PostgreSQL, PHP 8.4, Node 24,
воркер очереди и Mailpit работают в Docker. Vue/Inertia выбран для возможной админки
в одном Laravel-проекте; сам интерфейс заказов пока не реализован.

## Вебхуки и состояние заказа

HMAC считается по исходным байтам, сравнивается через `hash_equals`; подписанные строки
не изменяются middleware. Окно времени доставки — ±300 секунд, событие может быть старым.
Пустой секрет даёт 503, неверная подпись/время — 401, структура — 422, повторный ID
с другим содержимым — 409. Успех и безопасный повтор — 204.

Событие, заказ, позиции, история, уведомление и запись очереди сохраняются в одной
транзакции. Уникальные ключи защищают события и первые доставки заказа от дублей,
блокировка строки сериализует изменения одного заказа. При дедлоке транзакция
повторяется до трёх раз. Неизвестные типы сохраняются без применения, получают 204;
их повторная обработка после добавления поддержки — отдельная будущая задача.

**Как упорядочить изменения одной секунды?** Нужен монотонный номер версии.
Пока сравниваем `(order.updated_at, event.created_at, event.id)`. Лексикографический ID
служит только воспроизводимым разрешением ничьей, а не доказательством реального
порядка. Более свежее ручное исправление может вернуть статус назад. Позиции полностью
заменяются, `null` очищает поле. Деньги хранятся в DECIMAL, даты — в UTC.

**Как восстановить неполную историю?** Перестраиваем её из сохранённых снимков заказа
в порядке версий. Создание берём из `created_at`, пропущенную оплату — из `paid_at`,
отмену — из `cancelled_at`; доставку, получение и коррекции — из `updated_at`.
Последовательные одинаковые статусы объединяются. Неизвестные переходы невозможно
восстановить без журнала маркетплейса; время первого наблюдаемого статуса может быть
лишь временем снимка. Старое `paid_at` не переносит повторный переход назад во времени.

Допущения валидации: неотрицательные суммы с двумя дробными и до 12 целых цифр,
до 1000 позиций, целое количество 1–1 000 000, даты с секундами и явной зоной.
Метаданные оплаты/отмены должны попадать между созданием и изменением заказа.
Сумма маркетплейса сохраняется как есть; лимиты и проверку арифметического расхождения
следует согласовать отдельно.

## API

Email — точное совпадение без учёта регистра; пустые email/status не фильтруют.
При равном `created_at` сортировка идёт по ID. При новых заказах offset-страницы
могут сдвигаться. Карточка загружает позиции и историю под shared lock на заказе,
чтобы параллельный вебхук не смешал версии. `subtotal` считается через BigDecimal
из brick/math без float и переполнения целых. Nullable-поля остаются в ответе.

## Уведомления и сбои

**Что считать одинаковым письмом?** Принято: один тип письма на заказ за всё время,
независимо от ID события и смены email. Бизнесу нужно подтвердить это для повторной
оплаты/отправки после ручных исправлений. Уникальный `(order_id, type)` хранится в
`order_notifications`. Задание database-очереди записывается сразу в той же БД и
транзакции, поэтому нет разрыва между сохранением заказа и постановкой задания.
Подмена этой очереди Redis потребует отдельного диспетчера transactional outbox.

**Какое состояние считать текущим?** Последний принятый снимок на момент отправки.
Письмо разрешено только при соответствующем статусе `paid`, `shipped`, `cancelled`.
Устаревшее подавляется; ещё не отправленное может снова стать актуальным после
коррекции. Для доставки обязательны реквизиты отправки. Состав, сумма и email берутся
из свежего снимка. При отмене факт оплаты определяется по `paid_at` или истории;
неоплаченному заказу возврат не обещается. Уже отправленное письмо нельзя отозвать,
а ещё не поступившее изменение маркетплейса невозможно учесть заранее.

Сначала воркер фиксирует `sending` и уникальный ID попытки отдельной транзакцией,
затем повторно проверяет состояние под блокировкой заказа и отправляет письмо.
Во время SMTP блокировка удерживается; SMTP timeout — 3 секунды. Это компромисс:
медленная почта задерживает обработку вебхука того же заказа. Транзакция с SMTP
никогда автоматически не повторяется.

**Можно ли гарантировать exactly-once через SMTP?** Нет: сервер мог принять письмо,
а процесс упасть до фиксации результата. Приоритет отдан запрету дублей: ошибка
после начала попытки переводит её в `uncertain`, аварийное завершение может оставить
`sending`. Автоматической повторной отправки нет — возможна потеря письма даже при
сбое до фактической передачи. Команда `orders:notification-status` показывает такие
попытки для сверки с Mailpit/логами. Для надёжной доставки без этого компромисса нужен
почтовый провайдер с ключом идемпотентности и запросом результата отправки.

## Дальнейшая работа и ИИ

При росте нагрузки: быстрый durable inbox, фоновое применение событий, оптимизация
перестроения истории, метрики лимита ответа 5 секунд, мониторинг спорных отправок и
политика хранения персональных данных. Необязательная админка — отдельный этап.
Уведомления для существующих до миграции заказов автоматически не рассылаются.

`task/` восстановлена после форматирования starter kit и исключена из форматтеров:
эталон подписи зависит от точных байтов. Проверены HTTP-контракт, PHPUnit, статический
анализ, конкурентные процессы PostgreSQL и реальная SMTP-доставка в Mailpit.
ИИ использован для подготовки кода, тестов, документации и диагностики; допущения
и ограничения описаны явно, автоматические проверки не заменяют ревью.
